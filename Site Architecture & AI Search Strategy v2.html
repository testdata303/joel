Site architecture & AI search strategy — v2

Numberline · Growth engineering memo · Revised after IA review · July 2026

v2 applies one test to every piece of structure from v1: does it make today's ~40–60-page site simpler, or does it solve next year's problem early? The result is a smaller model — four content hubs instead of six — that still scales to thousands of pages, because hubs absorb growth on their index pages, not in the URL tree or the nav.

4Why use cases are their own type

Situation queries — "business phone that rings multiple cell phones," "keep my personal number private" — are how people phrase problems to AI assistants, and they're the queries where a small brand can win outright because the best answer is a specific setup, not a listicle. They don't fit the other types:

  • Not features — a situation usually composes several features (forwarding + shared texting + after-hours routing).
  • Not industries — the same situation cuts across plumbers, consultants, and law firms.
  • Not guides — the reader wants a working setup and a next step, not education.

Filing them under Learn (v1) would have made Learn a junk drawer of mixed intent by page 200. A dedicated type gives them a repeatable template today — which makes manual maintenance easier, since each new use case is a fill-in of a known shape — and gives industry pages their natural cross-link target ("Plumbers use these setups: …").

6Internal linking

Same three standardized blocks per page (breadcrumb with schema, descriptive in-body links, a "Related" block before the footer), with use cases added to the cross-type rules:

  • Industry pages → 2–3 features + 2 use cases common in that vertical + 1 learn guide.
  • Use-case pages → every feature in the setup + 1–2 industries where it's typical + 1 guide.
  • Feature pages → 2 use cases that showcase the feature + 1–2 industries + hub.
  • Learn pages → 2–3 features + 1–2 use cases or industries + 1 sibling guide.

Publish rule (unchanged): no page ships with fewer than 3 inbound links — hub index + 2 related pages, updated in the same commit.

9How this scales without reorganizing

  • 60 → 200 pages: nothing structural changes. Hub indexes gain sub-sections; footer columns stay capped and curated. The one planned promotion — features.html becomes the /features/ index — happens at the same URL.
  • 200 → thousands: still four hubs. Learn's index grows real sub-category sections (Guides / Business numbers / Scripts & templates / Etiquette); /for/ groups industries by category. If connections outgrow the Features index, that one section splits to /integrations/ with batch 301s — the single pre-designed escape hatch. /compare/ opens post-launch as pure addition.
  • AI search practices (unchanged from v1): canonical entity paragraph everywhere + Organization schema + llms.txt; a 40–60-word liftable answer under every H1; real-question FAQ blocks with FAQPage schema; depth over breadth while the domain is young; per-hub sitemap.xml segments; terminology discipline as entity hygiene; tag AI-assistant referrers in analytics from day one.

10Addendum — knowledge-graph review

Stress test before locking: if the goal is the world's best knowledge graph around business communications for small businesses — not an SEO site — does this architecture hold? Short answer: the folders hold; what's missing is an explicit topic layer on top of them. Folders are a filing system. The graph is expressed by pillar pages and links, and links don't care which folder a page lives in.

10.2 Are the hubs artificial SEO buckets?

Honest verdict: the four hubs are content types, not knowledge areas — /for/ = audience pages, /features/ = capability pages, /use-cases/ = situation pages, /learn/ = explainers. That is correct design, not a flaw: content types tell you what template a page uses and give URLs a permanent home; knowledge areas are the pillars in 10.1, and every pillar's children deliberately cross hub lines (Call Forwarding parents a feature page, three use cases, and a guide). The one real bucket risk is Learn as a catch-all — mitigated exactly by pillar ownership: a page's true parent is its pillar, and the Learn index groups by pillar, so the folder never has to carry meaning.

10.4 What to change: add the topic layer, touch nothing else

No URL, nav, or folder changes. Four editorial mechanisms turn the page collection into a graph:

  • Maintain a topic map. One flat editorial file — now created as topics.md at the repo root: every pillar, every child, every question each page answers, one URL per question. Since the site is maintained manually, this file — not a CMS — is the knowledge graph's source of truth. A proposed page that has no parent pillar in the map is a page that shouldn't be written.
  • One question, one URL, everywhere. The map assigns each question to exactly one page; every other page that touches the question links to it instead of re-answering it. This is the single biggest behavioral difference between a knowledge graph and an SEO page pile — no cannibalization, and AI engines see one authoritative answer per question.
  • Bidirectional pillar links as law. Every child links UP to its pillar on first mention (descriptive anchor, in the opening paragraph). Every pillar links DOWN to all its children in a structured "In this topic" section that grows over time — pillar pages, not folders, are the graph's real hubs. Add a "Part of:" line to the standard Related block.
  • One canonical definition per entity. Like the brand paragraph, each pillar term (business phone number, call forwarding, shared inbox…) gets a single reusable definition sentence used verbatim wherever the term is introduced. Consistent definitions across hundreds of pages are what make a model treat the site as the authority on the entity.

Locked, the model reads: four content-type folders for URL stability · ten topic pillars for meaning · links carry the graph. That combination is timeless — pillars and children can grow indefinitely without a single URL ever needing to move.
